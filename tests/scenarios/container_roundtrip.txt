# The withdraw/deposit round trip.
#
# This used to be session-only, on the belief that a container needs a real player and so could
# only be driven by hand from in-game chat. That was half right: it needs a player, but the player
# does not have to be a person. 'player spawn' connects a socketless client -- NetworkInfo is a
# four-method abstract class and the game ships InvalidNetworkInfo, which discards what it sends --
# so this now runs headless in the normal suite.
#
# The player is spawned here and disconnected at the end rather than once for the whole suite,
# deliberately: a connected player keeps regions loaded, and the persistence scenarios exist to
# catch exactly the bug that hides behind loaded regions.
#
harness player spawn

# Scenarios share one server boot, so start from no storage objects anywhere on the
# level -- clear only covers a radius, and expect total scans everything.
harness reset

harness clear 12

harness place terminal 4 0
harness place unit 5 0
harness place unit 5 1
harness fill 5 0 ironbar 40
harness fill 5 1 ironbar 40

harness expect units 4 0 2
harness expect total ironbar 80
harness expect held ironbar 0

harness open 4 0

# Withdraw is a move, so the network must lose exactly what the player gains.
harness withdraw ironbar 10
harness expect held ironbar 10
harness expect item 4 0 ironbar 70
harness expect total ironbar 70

# And back again. The totals returning to their starting values is the conservation check:
# an off-by-one that creates or destroys an item fails here even if the grid looks right.
harness deposit ironbar 10
harness expect held ironbar 0
harness expect item 4 0 ironbar 80
harness expect total ironbar 80

harness close

harness player despawn
